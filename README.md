# Extreme Weather — PM Addon (experimental)

**Minecraft 1.21.1 / NeoForge 21.1 / Java 21.** This is an addon for **ProtoManly's Weather 0.16.4-alpha** and **PMWeatherAPI 0.16.4.1 by nullved**. The old Forge 1.20.1 JAR and published v2.3.0 preview predate the current changes. To test this **unfinished branch**, download the `extremeweather-pm-neoforge-1.21.1` JAR artifact from a successful [CI run](https://github.com/romanata10/Weather-mod/actions/runs/42824791265) (GitHub sign-in may be required); this is not a vetted release. Install all three mods on every client and the server. PMWeather owns cloud formation, storm/tornado rendering, wind and weather sync: this addon must not duplicate its weather renderer. Native `/ew vortex` profiles now map near-ground outline width and ground/cloud taper into PMWeather's continuous width and `tornadoShape` controls rather than enum order; PMWeather still does not accept all 23 per-height profiles, so distinct requested silhouettes are not guaranteed. Joined-client CI 43064789244 observed native widths around 101 (wedge) and 22 (rope) at equal EF4, but reported taper values ~13.91 and ~15.84 respectively rather than the requested profile values; client-side taper fidelity remains unresolved. See [PMWeather](https://modrinth.com/mod/protomanlys-weather) and [PMWeatherAPI by nullved](https://modrinth.com/mod/pmweatherapi).

Full 17-point development plan: [docs/ROADMAP-ru.md](docs/ROADMAP-ru.md).

## Added by this addon

* Server-authoritative wildfire spread from lightning with bounded fire updates, destruction of vegetation and replacement of burned grass/dirt with scorched earth.
* Dense wildfire smoke plumes, PMWeather-native fire whirls in large fire clusters, particle embers and ash; when at least eight nearby fires are active, entities beneath the smoke gradually receive Poison. Rain extinguishes fires. Fire effects are shared by all multiplayer clients.
* Weather-derived local effects: hail damage, squall gusts, dust devils, weak waterspouts and landspouts, snow whirls, storm-driven swimmer movement, brief rainbow/sprite particles and small foam-ring whirlpools that apply server-side pull/swirl impulses to submerged entities (dedicated-server tested) and rare stronger lightning, three-second, fullbright red branching particle sprites anchored above nearby PMWeather storm clouds at night, coloured double rainbows and moving ball-lightning orbs. Stormy oceans have crest particles, server-side wind-driven bobbing of floating entities and boats, and bounded temporary water crests tracked across restarts; adjacent crest sources are rejected to reduce untracked vanilla source-water creation, and cleanup of the placed source is server-tested, including an actually unloaded and reloaded chunk in [CI 42962477576](https://github.com/romanata10/Weather-mod/actions/runs/42962477576). [CI 43014730733](https://github.com/romanata10/Weather-mod/actions/runs/43014730733) additionally verifies that a saved temporary crest survives a clean dedicated-server restart and `/ew clear all` then removes it. A separate contained-basin probe in [CI 43019036822](https://github.com/romanata10/Weather-mod/actions/runs/43019036822) observed vanilla lateral flow after a neighbor update and checked that this flowing block receded after source cleanup. Full downstream-flow rollback on arbitrary terrain, without a forced neighbor update, and crash recovery are **not** established. These are experimental additions, not PMWeather funnel models or a simulated fluid surface.
* Warm oceans can develop PMWeather-native cyclones with short-lived supplemental tropical spiral bands around existing storms, with a calm eye, native PMWeather wind **and cloud width** gradually weakened on landfall, and temporary storm-surge water. Naturally occurring PMWeather cyclones in warm/lukewarm ocean are now adopted without spawning a second native storm (joined-client CI 42821651272 confirmed a native supercell is not adopted, then counted one cyclone and one tracked system). The command-created system widens the same native PMWeather cyclone to at least 220 width units (server-state tested, including subsequent narrowing over land), rather than inventing a second cloud; CI 42754313079 captured a joined-client cyclone screenshot from outside the storm, but it shows only a broad bright cloud edge/haze rather than a clearly recognizable rotating cyclone; the requested giant visual appearance is **not validated**. Hurricane / typhoon / cyclone are regional labels for the same simplified system, not a complete meteorology model.
* Natural PMWeather squalls near players now receive bounded gust physics using the existing PMWeather cloud (no duplicate squall); spontaneous landspouts and waterspouts require a supercell/squall cloud near their actual spawn point, not just arbitrary cyclone proximity. These natural paths still need joined-client visual validation.
* Natural PMWeather supercells that already reach stage 3 with windspeed at least 65 can be assigned a deterministic, weighted outline preset near players, without a command, a second funnel, or extra wind; PMWeather retains control of their cloud width, growth and decay. The weather-radar block reports the selected preset (or unknown for other storms), **not** a verified visible silhouette. For naturally adopted storms, the native `tornadoShape` control now blends from a rope-like value toward the selected mature preset over 80 ticks as PMWeather wind increases, and back toward rope-like values as wind weakens; it does not force the native wind or cloud width. This numerical transition is not yet visually verified as a rope-shaped birth/death sequence; verified 23-form rendering is still missing.
* A radar and storm siren that use PMWeatherAPI `NearbyStorms`; an anemometer reading PMWeather wind, a barometer block that currently reports nearby storm count rather than fabricated pressure (physical pressure unavailable), plus scorched earth, charred grass and ash blocks. Interact with the instrument blocks to read them. The siren polls nearby PMWeather storms every second, rings on activation and emits redstone power 15 while active. Crafting recipes for all four instruments are included.

**Not yet implemented:** realistic tsunami fluid dynamics (a rare cyclone pressure-wave pulse can briefly push entities and raise bounded water crests), physically simulated tropical-cyclone pressure/wind fields, EF shape overrides, multi-vortex special effects, fully simulated lightning entities, additional PMWeather-native funnel shapes, physical fluid waves, sound design and additional functional blocks. PMWeather itself supplies its own clouds, storms and tornadoes. Small vortices now request PMWeather particle texture resources from the installed PMWeather JAR at runtime; the addon does not ship or copy its textures. PMWeather FIRE_SMOKE, EMBER, FLAME and FOAM particle types are reused for applicable fire/water effects. The four weather instruments now use original 32x32 top/side/bottom textures (regenerate with `python3 scripts/gen_textures.py`). This is a development preview, **not** a complete version of the 17-feature specification. Do not claim PMWeatherAPI itself provides the missing effects.

## Build and run

Install Java 21 and Gradle 8.8, then run `gradle build`. The GitHub Actions workflow builds, checks PMWeather and original addon particle texture IDs, boots a dedicated server, invokes PMWeather storm/native-vortex and positional disaster commands via RCON, verifies wildfire changes a world block, a flood crest places water, and a PMWeather-cloud squall imparts measurable horizontal velocity to a test mob (headless servers without players can suspend actual entity movement), and runs an optional Xvfb client probe; automatic preview JAR publication is disabled. Manual client-side graphics/multiplayer gameplay review is still required. Back up worlds before enabling wildfires. MIT license applies to *this addon only*; PMWeather and PMWeatherAPI retain their own licenses. No code or textures from those projects are redistributed here.

## Operator commands (experimental)

* `/ew storm <pm_type> [risk]` — invoke a **native PMWeather** storm via PMWeatherAPI `StormBuilder`; tab completion lists types exposed by the installed PMWeather version, and risk is 0–100. This does not force a tornado or override PMWeather's native rendering.
* `/ew vortex <shape> <ef>` — create a **native PMWeather supercell** and set its public tornado shape, width and stage parameters, synchronized through PMWeather. No second addon silhouette is spawned: PMWeather renders the only funnel. PMWeather still decides the actual funnel: the 23 names are approximate numeric presets, **not 23 native PMWeather mesh types**. Multi-vortex, braided, dead-man-walking and El Reno presets add PMWeather-native satellite `Vorticy` instances to that one storm; a dedicated-server test checks their state. [CI 43021173054](https://github.com/romanata10/Weather-mod/actions/runs/43021173054) captured a joined-client multi-vortex frame: the central funnel is visible, but four distinct satellites are **not** visually confirmed. A wider native satellite orbit was tried in [CI 43022549675](https://github.com/romanata10/Weather-mod/actions/runs/43022549675); its frame still does not resolve four separate funnels, so this preset remains experimental. [CI 43025792989](https://github.com/romanata10/Weather-mod/actions/runs/43025792989) additionally logs that the joined client received all four native `Vorticy` instances; synchronization is confirmed, but visual separation is not. [CI 43029279058](https://github.com/romanata10/Weather-mod/actions/runs/43029279058) captured the SAME storm from a higher spectator angle without spawning another one; four distinct funnels still cannot be identified in that frame. Supported names: `wire`, `rope`, `needle`, `v_shaped`, `cigar`, `cylinder`, `cone`, `landspout`, `concave_sided`, `straight_sided`, `convex_sided`, `segmented`, `truncated_cone`, `drill_shaped`, `bowl_shaped`, `wedge`, `plume_base`, `hourglass`, `braided`, `looping`, `multi_vortex`, `dead_man_walking`, `el_reno`.
* `/ew outline <shape> <ef>` — optional addon silhouette alone, without a PMWeather supercell. It references PMWeather textures at runtime but uses original addon geometry and physics.
* `/ew disaster <name>` — `hail`, `rainbow`, `sprite`, `ball_lightning`, `superbolt`, `squall`, `dust_devil`, `waterspout`, `landspout`, `snow_whirl`, `fire_whirl`, `hurricane`, `typhoon`, `cyclone`, `meteotsunami`, `tsunami`, `surge`, `flood`, `whirlpool`, `wildfire`, `forest_fire`. Commands also accept explicit coordinates: `/ew disaster <name> <x> <y> <z>` works from the server console. Effects return an error when prerequisites (water, loaded chunk, storm capacity) are absent.
* `/ew ignite <x> <y> <z>` — operator wildfire ignition at loaded coordinates (also usable from the server console).
* `/ew status` — count nearby native storms, PMWeather sub-vortices and tracked wildfire blocks. `/ew clear` removes only addon outlines; `/ew clear all` clears native PMWeather storms, active addon effects, wildfire sources and temporary surge water in the current dimension (operator-only).

**Shape attribution:** The user supplied a tornado-type reference chart. `/ew vortex` now configures an actual PMWeather supercell through public storm fields and PMWeather server sync. Because PMWeather exposes a continuous tornadoShape float, not an enum for every chart label, exact 23 distinct native silhouettes remain unverified. The initial native-wedge screenshot in CI run 42833774358 showed only haze. After initializing PMWeather's wind/energy as well as stage/width, the joined-client screenshot in [CI run 42953287277](https://github.com/romanata10/Weather-mod/actions/runs/42953287277) **does show one visible native funnel**. In [CI run 42957006690](https://github.com/romanata10/Weather-mod/actions/runs/42957006690), separate joined-client frames show a visibly broader wedge and a narrower rope from two separate native PMWeather storms; they are not two overlapping effects. Both remain gray/stylized, not verified photorealistic reference forms or 23 distinct silhouettes. The mandatory server test separately checks that native wind and width persist for ten seconds; client frames still require visual review. `/ew outline` remains a separate, optional addon particle effect and is not part of `/ew vortex`; no imagery or textures from PMWeather are copied.

### PMWeather renderer limitations (important)

The dependency exposes four native storm types: `SUPERCELL`, `SQUALL`, `CYCLONE`, `FIRE_WHIRL`, plus scalar `Storm.tornadoShape`/width and native sub-vortex state. It does **not** expose a documented 23-shape deformation interface or a cloudless native waterspout/landspout/dust-devil storm type. `/ew vortex` now creates **only one** PMWeather supercell, never a second matching particle funnel; requested names are parameter presets, **not verified exact visual shapes**. The small-vortex modes remain separate addon effects using runtime PMWeather textures. SQUALL and CYCLONE use PMWeather-native storm cloud types. Command-created cyclones now set the native storm width, but a giant *visually verified* rotating cloud deck, realistic tsunami and PMWeather raymarch-color hooks remain unimplemented. Do not describe this preview as completing all the requested changes.

This confirms the rendering *path*, not that the vortex is visibly correct or matches reference images. The in-world step remains `continue-on-error`, so inspect its result separately. Release publication stays manual.

The renderer still uses one camera-facing 2.5D plane, and PMWeather clouds/rain can obscure it; these captures are diagnostic, not visual approval. This confirms the shader reaches the screen, but the silhouette is rudimentary and does **not** match the requested realistic PMWeather raymarched appearance.
